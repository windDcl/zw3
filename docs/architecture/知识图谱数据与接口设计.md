# 知识图谱数据与接口设计

## 1. 文档目标

本文档在《政务问答系统知识图谱落地方案》的基础上，细化知识图谱建设所需的数据模型、接口结构、返回格式与后端 DTO 建议，作为开发实施的直接依据。

## 2. 存储分工

### 2.1 MySQL 存储内容

继续保留在 MySQL 中的数据：

1. FAQ 主表与别名表
2. 分类、公告、日志、未命中问题
3. 系统设置
4. FAQ 与图谱节点的挂接关系

### 2.2 Neo4j 存储内容

建议放入 Neo4j 的数据：

1. 图谱节点
2. 图谱关系
3. 节点别名
4. 节点扩展属性
5. FAQ 主题节点与事项节点的图内映射关系

### 2.3 为什么不把所有数据都放进图数据库

原因如下：

1. 当前系统的 FAQ、日志、后台管理已经基于 MySQL 成型。
2. 图数据库更适合关系遍历和路径查询，不适合替代现有业务表。
3. FAQ 与图谱之间存在“业务挂接”语义，放 MySQL 更利于后台维护和审计。

## 3. MySQL 数据设计

### 3.1 FAQ 与图谱挂接表

表名建议：`faq_graph_link`

```sql
CREATE TABLE faq_graph_link (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  faq_id BIGINT NOT NULL COMMENT 'FAQ主键',
  graph_node_id VARCHAR(64) NOT NULL COMMENT '图谱节点ID',
  graph_node_type VARCHAR(32) NOT NULL COMMENT '节点类型，通常为Matter',
  is_primary TINYINT NOT NULL DEFAULT 1 COMMENT '是否主绑定',
  sort_order INT NOT NULL DEFAULT 0 COMMENT '展示顺序',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_faq_id (faq_id),
  KEY idx_graph_node_id (graph_node_id)
) COMMENT='FAQ与知识图谱节点挂接表';
```

### 3.2 字段规则

| 字段 | 规则 |
| --- | --- |
| `faq_id` | 必须关联现有 FAQ 主键 |
| `graph_node_id` | 对应 Neo4j 中节点唯一业务 ID |
| `graph_node_type` | 建议冗余保存，便于后台筛选 |
| `is_primary` | 每个 FAQ 至少允许一个主节点 |
| `sort_order` | 控制前端图谱展示优先级 |

### 3.3 推荐约束

建议在业务层增加以下约束：

1. 同一 FAQ 只能有一个主绑定节点。
2. 同一 FAQ 不允许重复绑定同一节点。
3. 被停用 FAQ 的图谱挂接仍保留，但前台不参与展示。

## 4. Neo4j 节点设计

### 4.1 节点标签与业务含义

| 标签 | 业务含义 |
| --- | --- |
| `Matter` | 办理事项 |
| `Material` | 材料 |
| `Condition` | 条件 |
| `Channel` | 渠道 |
| `Department` | 部门 |
| `Policy` | 政策依据 |
| `PersonType` | 适用人群 |
| `Region` | 地区 |
| `Outcome` | 办理结果 |
| `FaqTopic` | FAQ 图谱入口主题 |

### 4.2 节点公共属性

所有节点统一建议包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bizId` | String | 业务唯一 ID，供后端使用 |
| `name` | String | 展示名称 |
| `type` | String | 节点类型 |
| `summary` | String | 简短摘要 |
| `status` | Integer | 1 启用，0 停用 |
| `source` | String | 数据来源 |
| `regionCode` | String | 地区编码 |
| `aliases` | List<String> | 节点别名 |
| `createdAt` | String | 创建时间 |
| `updatedAt` | String | 更新时间 |

说明：

1. `bizId` 不建议直接依赖 Neo4j 内部 ID。
2. 节点名称支持别名，便于问句匹配与后台搜索。
3. `regionCode` 先做可选字段，为地区化扩展做准备。

### 4.3 不同节点的扩展属性建议

#### Matter

| --- | --- |

#### Material

#### Condition

| --- | --- |

#### Channel

| 字段 | 说明 |
| --- | --- |
| `channelType` | 线上/线下 |
| `onlineUrl` | 在线办理地址 |
| `address` | 线下地址 |

#### Department

| 字段 | 说明 |
| --- | --- |
| `departmentCode` | 部门编码 |
| `contactPhone` | 联系电话 |

#### Policy

| 字段 | 说明 |
| --- | --- |
| `policyNo` | 文件编号 |
| `publishOrg` | 发布单位 |
| `effectiveDate` | 生效日期 |
| `expireDate` | 失效日期 |

## 5. Neo4j 关系设计

### 5.1 关系类型定义

| 关系类型 | 起点 | 终点 | 展示标签 |
| --- | --- | --- | --- |
| `REQUIRES_MATERIAL` | Matter | Material | 需要 |
| `HAS_CONDITION` | Matter | Condition | 条件 |
| `HANDLED_BY` | Matter | Department | 办理部门 |
| `AVAILABLE_AT` | Matter | Channel | 办理渠道 |
| `APPLIES_TO` | Matter | PersonType | 适用对象 |
| `BASED_ON` | Matter | Policy | 政策依据 |
| `RESULTS_IN` | Matter | Outcome | 办理结果 |
| `BELONGS_TO_REGION` | Any | Region | 适用地区 |
| `RELATED_TO` | Any | Any | 相关 |
| `FAQ_MAPPED_TO` | FaqTopic | Matter | 映射到 |

### 5.2 关系属性

建议所有关系统一包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `bizId` | String | 关系唯一 ID |
| `relationType` | String | 关系类型 |
| `label` | String | 前端展示文案 |
| `sortOrder` | Integer | 展示顺序 |
| `status` | Integer | 1 启用，0 停用 |
| `source` | String | 数据来源 |
| `createdAt` | String | 创建时间 |
| `updatedAt` | String | 更新时间 |

## 6. Neo4j 建模示例

### 6.1 节点示例

```cypher
CREATE (m:Matter {
  bizId: 'matter_1001',
  name: '公积金提取',
  type: 'Matter',
  summary: '住房公积金提取办理事项',
  status: 1,
  source: 'manual',
  aliases: ['公积金怎么领取', '公积金怎么提取'],
  createdAt: '2026-05-06 21:00:00',
  updatedAt: '2026-05-06 21:00:00'
});
```

### 6.2 关系示例

```cypher
MATCH (m:Matter {bizId:'matter_1001'}), (n:Material {bizId:'material_2001'})
CREATE (m)-[:REQUIRES_MATERIAL {
  bizId: 'edge_3001',
  relationType: 'REQUIRES_MATERIAL',
  label: '需要',
  sortOrder: 1,
  status: 1,
  source: 'manual',
  createdAt: '2026-05-06 21:00:00',
  updatedAt: '2026-05-06 21:00:00'
}]->(n);
```

## 9. 推荐 Cypher 查询

### 9.1 查询事项一跳图谱

```cypher
MATCH (m:Matter {bizId: $matterId})-[r]->(n)
WHERE r.status = 1 AND n.status = 1
RETURN m, r, n
ORDER BY r.sortOrder ASC
LIMIT 20;
```

### 9.2 查询节点详情

```cypher
MATCH (n {bizId: $nodeId})
RETURN n;
```

### 9.3 查询事项到结果的路径

```cypher
MATCH p = shortestPath((a {bizId: $fromId})-[*..4]->(b {bizId: $toId}))
RETURN p;
```

### 9.4 按节点名或别名搜索

```cypher
MATCH (n)
WHERE n.name CONTAINS $keyword OR ANY(alias IN n.aliases WHERE alias CONTAINS $keyword)
RETURN n
LIMIT 20;
```

## 10. 接口实现优先级

建议实现顺序如下：

1. `POST /api/public/ask` 扩展返回图谱结构
2. `GET /api/public/graph/matter/{id}`
3. `GET /api/public/graph/node/{id}`
4. `GET /api/admin/graph/faq-links/{faqId}`
5. `POST /api/admin/graph/faq-links`
6. 节点与关系 CRUD
7. 路径查询与关联 FAQ 查询

## 11. 验收口径

数据与接口层面的第一阶段验收标准建议为：

1. FAQ 命中后，返回结果中包含图谱中心节点、节点列表、边列表。
2. 前端可根据 `nodes + edges` 直接绘制关系图。
3. 一个 FAQ 至少能绑定一个事项节点。
4. 后台可查询和维护 FAQ 的图谱挂接关系。
5. 至少支持一跳图谱查询与节点详情查询。
